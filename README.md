# churn-baseline — отток с подбором порога

Предсказание оттока на Telco Customer Churn: кросс-валидация трёх моделей, подбор порога по
out-of-fold вероятностям, обучение, скоринг базы и проверка артефактов. Данные публичные, все цифры
воспроизводятся одной командой с фиксированным `SEED = 42`.

Задача не в том, чтобы выжать лидерборд. Отток — это редкий класс (26,5 %) и цена ошибок разная:
пропустить уходящего клиента дороже, чем лишний раз дёрнуть лояльного. Поэтому здесь вместе с
ROC AUC считается PR AUC, а рабочая точка выбирается по F1, а не по умолчанию 0,5.

## Пайплайн

```text
data/Telco-Customer-Churn.csv ──▶ 21 признак ──▶ CV, 5 фолдов ──▶ лучшая модель ──▶ work/model.pkl
     7043 × 21                    add_features       3 модели       по ROC AUC        work/metrics.json
                                                                          │
                                        work/scores.csv ◀─────────────────┘ predict
                                     вероятности и метки                   │
                                                                          ├──▶ check: 6 проверок, exit 0 или 4
                                                                          └──▶ прогноз без метрик: порог 0.5
```

## Установка и запуск

Нужен Python 3.9+ и `pandas` + `scikit-learn` (проверено на 3.11, pandas 2.2.3, scikit-learn 1.9.1).

```bash
py -3 churn.py fetch                     # скачать датасет и сверить sha256
py -3 churn.py train                     # CV трёх моделей, work/metrics.json + work/model.pkl
py -3 churn.py predict --holdout 0.2     # проверка на отложенной выборке
py -3 churn.py predict                   # скоринг всей базы сохранённой моделью
py -3 churn.py check                     # проверить артефакты и согласованность
```

Пути по умолчанию: `data/Telco-Customer-Churn.csv`, `work/model.pkl`, `work/metrics.json`,
`work/scores.csv`. Порог берётся из `work/metrics.json`; если файла метрик нет, `predict` работает
с 0,5 и не притворяется, что порог подобран.

## Данные

`data/Telco-Customer-Churn.csv` — публичный набор IBM, 7043 строки, 21 колонка, 970 457 байт,
sha256 `16320c9c…e3055e91`. Ушедших 1869 (26,54 %). Пропусков нет, но в `TotalCharges` 11 пустых
строк — все при `tenure = 0`, то есть это новые клиенты, а не битые данные. Дублей `customerID` нет.
Файл в репозиторий не кладётся: `fetch` скачивает его и сверяет хеш, так что подменить данные
молча не получится.

Категориальные значения чистые: `gender` 2, `Contract` 3, `InternetService` 3, `PaymentMethod` 4.
`tenure` от 0 до 72 месяцев, `MonthlyCharges` от 18,25 до 118,75.

## Признаки (21)

```text
числовые (6):  SeniorCitizen, tenure, MonthlyCharges, TotalCharges, charges_per_month, services_count
категориальные (15): gender, Partner, Dependents, PhoneService, MultipleLines, InternetService,
  OnlineSecurity, OnlineBackup, DeviceProtection, TechSupport, StreamingTV, StreamingMovies,
  Contract, PaperlessBilling, PaymentMethod
```

`charges_per_month = TotalCharges / tenure` — средний чек за месяц жизни клиента; при `tenure = 0`
берётся `MonthlyCharges`, иначе деление на ноль. `TotalCharges` приходит строкой, пустые значения
превращаются в `NaN`. `services_count` считает, сколько из восьми услуг подключено (`Yes`), —
это дешёвый прокси глубины «привязки» клиента.

Числовые заполняются медианой и масштабируются, категориальные — самым частым значением и one-hot
(`handle_unknown="ignore"`). И то, и другое внутри `Pipeline`, поэтому медиана и словарь категорий
считаются по обучающему фолду и не утекают из валидации.

## Дисбаланс и порог

Классов 26,5 % против 73,5 %, поэтому у всех трёх моделей включён `class_weight="balanced"`
(у леса `balanced_subsample`): модель видит вес обратно пропорционально частоте класса.

Порог не 0,5. Сетка 0,05…0,95 с шагом 0,01 прогоняется по out-of-fold вероятностям, для каждой точки
считается F1, выбирается лучшая. `train` пишет этот порог в `work/metrics.json`, `predict` его
применяет, `check` проверяет, что метки в `scores.csv` действительно получены из вероятностей
именно этим порогом — расхождение даёт код 4.

## Кросс-валидация (5 фолдов, стратифицированно)

| Модель | ROC AUC | PR AUC | Accuracy @ 0,5 | Порог | F1 @ порог |
| --- | --- | --- | --- | --- | --- |
| LogisticRegression (balanced) | **0,8446 ± 0,0132** | **0,6540** | 0,7453 | 0,57 | 0,6329 |
| RandomForest, 400 деревьев | 0,8411 ± 0,0123 | 0,6477 | **0,7796** | 0,42 | 0,6290 |
| HistGradientBoosting | 0,8288 ± 0,0091 | 0,6310 | 0,7599 | 0,33 | 0,6118 |

Логистическая регрессия выигрывает по ROC AUC и PR AUC, лес — по accuracy при пороге 0,5.
Разрыв между ними (0,845 против 0,841 при σ ≈ 0,013) меньше разброса фолдов, то есть это шум,
а не преимущество. `train` выбирает модель по ROC AUC: на редком классе это честнее accuracy,
которая почти целиком определяется большинством.

Высокая accuracy у леса — прямое следствие более осторожных меток: при пороге 0,42 он помечает
меньше клиентов и реже ошибается на лояльных, но и уходящих ловит не лучше. Поэтому в основе —
ранжирование, а не доля верных ответов.

## Проверка на отложенной выборке

20 % (1409 строк) отложены стратифицированно, обучение на остальных, порог из `metrics.json`:

```bash
py -3 churn.py predict --holdout 0.2
rows=1409 flagged=508 thr=0.57 ACC=0.7630 AUC=0.8414
```

AUC совпадает с CV (0,8414 против 0,8446), accuracy 0,7630 — та же картина: порог 0,57 смещает
метки в сторону «уйдёт», из-за чего растёт recall и падает accuracy. Это ожидаемо и есть плата
за рабочую точку.

## Скоринг базы

```bash
py -3 churn.py predict

```

`work/scores.csv` — три колонки: `customerID, churn_probability, churn_pred`. 2538 клиентов (36,0 %)

вероятность отсортирована, порог отсекает хвост. Файл перезаписывается при каждом запуске.

## Границы

- Kaggle-балл не получен: соревнование требует токена и отправки, здесь только локальный пайплайн.
  Модели и порог воспроизводятся, лидерборд — нет, и в README он не заявлен.
- Гиперпараметры не подбирались: 400 деревьев, 300 итераций бустинга и `C` логистической регрессии
  взяты по умолчанию/на глаз. Систематический тюнинг на 7043 строках даст прирост в пределах шума
  фолдов, а не качественный скачок.
- Датасет синтетический по происхождению (IBM сгенерировала его для демонстрации), поэтому
  абсолютные вероятности — не про реальных клиентов; переносить порог 0,57 на живую базу нельзя,
  его надо пересчитывать на своих данных.
- `charges_per_month` при `tenure = 0` равен `MonthlyCharges`, и это единственное место, где
  признак опирается на предположение, а не на расчёт.
- Порог оптимизируется по F1 на OOF. Если цена ложного срабатывания другая (например, скидка
  удержания стоит дорого), порог надо пересчитать под стоимость ошибок, а не под F1.
- `RandomForest` и бустинг используют `n_jobs=-1`; на слабой машине CV займёт заметно дольше,
  результат при этом не изменится.
